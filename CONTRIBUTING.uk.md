# Як долучитися

[English](CONTRIBUTING.md) · **Українська**

## Куди йде зміна і як вона виходить

Процес змін, реліз і відкат описано в [Зміни в наборі](docs/changing.uk.md): до якого шару
належить зміна, як випробувати плагін із проєкту до злиття і як переміщення тегу `stable` робить
реліз.

## Перед pull request

| ID | Перевірка | Команда |
| --- | --- | --- |
| 1 | Встановити інструменти репозиторію | `npm ci` |
| 2 | Схема, вендорені копії, тести, перевірка назв | `npm run check` |
| 3 | Маніфести плагінів і маркетплейсу | `claude plugin validate .` |

1. **Лише нейтральні назви.** Репозиторій публічний. Жодних назв, посилань чи нотаток із приватних
   проєктів або від роботодавців у файлах, комітах, назвах гілок чи pull request. Використовуйте
   `my-app`, `APP-123`.
2. **Без `version` у `plugin.json`.** Реліз — це тег `stable`.
3. **Спільний код** редагують у `shared/` і копіюють у кожен плагін командою `npm run vendor`.
4. **Документи йдуть парами**: `name.md` і `name.uk.md` з однаковою структурою.

## Перевірка назв

`scripts/naming-guard.mjs` падає на заборонених термінах у відстежуваних файлах, повідомленнях
комітів, рядках автора і назві гілки. Список термінів ніколи не комітять: CI читає секрет
`NAMING_GUARD_WORDS`, а локальний запуск — `~/.config/agent-kit/naming-guard.txt` (один термін
на рядок; синтаксис — у заголовку скрипта). Pull request із форків не отримують секретів, тож
перевірка там падає, доки супровідник не перезапустить її.
