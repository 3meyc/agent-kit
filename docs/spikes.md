# Plugin behaviour spikes

**English** · [Українська](spikes.uk.md)

The design in [architecture.md](architecture.md) and [changing.md](changing.md) relies on Claude
Code plugin behaviour. This page records what real runs showed, so later work builds on facts
rather than on the docs alone.

## Method

| ID | Item | Value |
| --- | --- | --- |
| 1 | Claude Code | CLI 2.1.300, macOS |
| 2 | Plugins | Throwaway plugins and marketplaces, never merged |
| 3 | Sandbox | A scratch git repo outside every project; installs at `--scope local`; removed afterwards |
| 4 | Runs | Headless `claude -p`. Where no model answer is needed, the session transcript (`~/.claude/projects/<dir>/<id>.jsonl`) shows exactly what was rendered into context |
| 5 | Remote refs | Temporary `spike-w03-*` tags on this repo, deleted afterwards |
| 6 | Model | Sonnet (`--model sonnet`) for runs that need a model answer (S1a check, S2, S4b); Haiku for the rest. The user-level plugins and hooks of the test machine stayed active |

## Results

| ID | Question | Result | Evidence | Fallback or consequence |
| --- | --- | --- | --- | --- |
| S1a | Does a plugin `SessionStart` hook's stdout load as context in that session? | yes | Plugin hook `echo "SPIKE-CONTEXT: ..."`; the transcript renders `<system-reminder>SessionStart:startup hook success: SPIKE-CONTEXT: the session codeword is PELICAN-42.</system-reminder>` before the first prompt; asked "What is the session codeword?", the model answered `PELICAN-42` | Use it for always-on kit text. It is injected once per session start (and again on resume, clear or compact, which fire `SessionStart` again) |
| S1b | Does a hook that writes git-ignored `.claude/rules/kit-*.md` get them loaded in the same session? | partial | Same run wrote `kit-spike.md` (no `paths:`): the `instructions` attachment lists only `~/.claude/CLAUDE.md`; next session it lists `.claude/rules/kit-spike.md`. A hook-written rule **with** `paths: ["**/*.svelte"]` did load in the same session: `nested_memory .../.claude/rules/kit-spike-svelte.md` after `@src/App.svelte` | Always-on text: hook stdout (S1a). Path-scoped rules: hook-written files work from the first session. Unconditional rule files only from the next session |
| S2 | Does a skill reliably replace a `paths:`-scoped rule? | yes | Rule: `.claude/rules/svelte.md` with `paths: ["**/*.svelte"]` (mark the last line `<!-- conv:rule -->`). Skill: plugin skill `spk-svelte` with the same `paths:` (mark the first line `<!-- conv:skill -->`). One active at a time, `claude -p <prompt> --permission-mode acceptEdits`, 5 runs per cell. Edit `src/App.svelte`: rule 5/5, skill 5/5. Create `src/Counter.svelte`: rule 5/5, skill 5/5. Prompt that never names Svelte ("The home page greeting should say Hello Kit…"): rule 5/5, skill 5/5; the Skill tool was called in every skill run (`"name":"Skill"`, `spk-core:spk-svelte`). Two earlier batches of this prompt were broken by shell approval prompts; in every run of those that did edit the file, the convention was followed (rule 6/6, skill 5/5) | Use skills with `paths:` in plugins. Unlike a rule, the skill body loads only when the model calls it, and its description is listed in every session (side finding 2), so keep the description short and specific. 5 runs per cell on one model is a small sample: recheck on the model in use if a convention starts slipping |
| S3a | Does a plugin in marketplace B resolve a dependency on a plugin in marketplace A? | partial | With `"allowCrossMarketplaceDependenciesOn": ["spike-a"]` in B and A added: `claude plugin install spk-overlay@spike-b --scope local` → `Successfully installed plugin: spk-overlay@spike-b (scope: local) (+ 1 dependency: spk-core)`. A not added: `Warning: dependency "spk-core@spike-a" was not installed (no marketplace you have added lists it)`. Allowlist removed: install succeeds, then `claude plugin list` → `Status: ✘ failed to load ... Dependency "spk-core@spike-a" is not installed` | The overlay marketplace must list the base in `allowCrossMarketplaceDependenciesOn`, and every project must also declare the base marketplace (both in `extraKnownMarketplaces` of `.claude/settings.json`). `kit doctor` should check both |
| S3b | Can one repo serve two channels (stable and latest)? | partial | Project 1 adds `owner/repo#spike-w03-stable`, project 2 adds `#spike-w03-latest` (same marketplace `name`): `Marketplace 'spike-gh' was already added from ...@spike-w03-stable and now points at ...@spike-w03-latest`. Then `claude plugin update` in project 1 → `updated from 0bc8f88e1ac3 to 398615c91fe8` (the latest build). With a separately named latest catalog served as a raw URL (`https://raw.githubusercontent.com/<owner>/<repo>/<ref>/channels/latest.json`, `git-subdir` sources pinned to `ref`), both projects ran side by side: `GH-BUILD: v1` and `GH-BUILD: v2` | The marketplace clone is per user (`~/.claude/plugins/known_marketplaces.json`), so one name means one channel per machine. Serve `latest` as a second catalog with its own name (for example `agent-kit-latest`) from the same repo. Overlays depend on `@agent-kit` (stable) only |
| S3c | Does `marketplace add owner/repo#ref` pin to a tag? | yes | `known_marketplaces.json` → `"ref": "spike-w03-stable"`; `installed_plugins.json` → `"version": "0bc8f88e1ac3"`, `"gitCommitSha": "0bc8f88e..."` (the tagged commit); hook prints `GH-BUILD: v1` | None needed. With no `version` field the cache key is the 12-character commit SHA |
| S4a | Is `${CLAUDE_PLUGIN_ROOT}` substituted in skill and command bodies? | yes | `claude -p "/spk-core:spk-root"` → expanded prompt `PLUGIN_ROOT_IN_SKILL=/…/plugins/spk-core`; `/spk-core:spk-cmd` → `PLUGIN_ROOT_IN_COMMAND=/…/plugins/spk-core`; a GitHub-installed copy → `GH_PLUGIN_ROOT=/Users/…/.claude/plugins/cache/spike-gh/spk-gh/fb0a38b5b7e0` | None needed. `${CLAUDE_SKILL_DIR}` is substituted too |
| S4b | Is a plugin's `bin/` on the Bash tool's PATH? | yes | `claude -p "Run the shell command 'spk-bin' with the Bash tool…"` → Bash ran bare `spk-bin` → `SPK-BIN-OK from /…/plugins/spk-core/bin/spk-bin`; `command -v spk-gh-bin` → `/Users/…/.claude/plugins/cache/spike-gh/spk-gh/fb0a38b5b7e0/bin/spk-gh-bin` | None needed. The plugin variables themselves are not in the Bash environment (docs), so scripts that skills call go in `bin/` or are written as `${CLAUDE_PLUGIN_ROOT}/…` in the skill body |
| S5a | Do plugin hooks and project hooks both fire, and in which order? | yes | `.hooklog` over 5 runs, every run: `project-ss` then `plugin-ss` (SessionStart), `project-ups` then `plugin-ups` (UserPromptSubmit). Context order: `PROJECT-CONTEXT` reminder before `SPIKE-CONTEXT` | Hooks run in parallel; the project hook started first in 5/5 runs, but nothing guarantees it. Don't make kit hooks depend on project hooks having run |
| S5b | Can a project switch off one plugin hook? | no | `"disableAllHooks": true` in `.claude/settings.json` → no hook fired at all, project ones included. `"enabledPlugins": {"spk-core@spike-a": false}` in project settings → plugin hooks still fired, because the local-scope `true` wins | Each kit hook script checks an opt-out in `kit.json` (for example `"hooks": {"off": ["ledger-stop"]}`) and exits 0. Disabling the whole plugin stays possible from `.claude/settings.local.json` |
| S6 | Can `claude plugin marketplace add <org>/<overlay-repo>` clone a private repo while the active gh account is the personal one? | no | No SSH key, so Claude Code clones over HTTPS. The clone dir is `~/.claude/plugins/marketplaces/`, outside `~/DEV`, so no `includeIf` helper applies and the keychain answers with the personal account: `HTTPS (https://github.com/<org>/<overlay-repo>.git): ... remote: Repository not found`. With the fix below injected for one command through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n` (no config file changed), the clone succeeded and stopped only at `Marketplace file not found at …/.claude-plugin/marketplace.json` (the manifest doesn't exist yet) | Proposed, not applied: a per-org credential helper in `~/.gitconfig`: `[credential "https://github.com/<org>"]` with `helper = !f(){ echo username=x-access-token; echo password=$(gh auth token --user <work-account>); }; f` and `useHttpPath = true` |
| S7 | Does `claude --plugin-dir <local plugin>` override an installed plugin of the same name? | yes | `claude -p x --plugin-dir <copy> --debug-file …` → `Plugin "spk-core" from --plugin-dir overrides installed version`; only the override's hook ran (`codeword is LOCAL-OVERRIDE-99`, one `plugin-ss` line) | None needed. `claude plugin list` still shows the installed copy as enabled, so check the debug log or the behaviour |
| S8 | After a pinned tag moves, does the next session pick up the new commit with auto-update on? | no | Tag `spike-w03-move` moved from v1 to v3, `"autoUpdate": true` on the marketplace entry. Two later `claude -p` sessions: `GH-BUILD: v1`. `claude plugin marketplace update spike-gh` → clone at `fb0a38b` (v3), next session still `GH-BUILD: v1`. `claude plugin update spk-gh@spike-gh --scope local` → `updated from 0bc8f88e1ac3 to fb0a38b5b7e0`, next session `GH-BUILD: v3` | Headless sessions never run the auto-update pass; interactive ones run it after the first message, after a random delay of up to ten minutes, and apply it at the next launch (docs). A release note says: run `claude plugin marketplace update agent-kit` and then `claude plugin update <plugin>@agent-kit`. `kit doctor` can compare the installed SHA with the tag |
| S9a | Does pnpm install a git dependency pinned to a tag (`github:owner/repo#tag`)? | yes | `pnpm add 'github:<owner>/<repo>#spike-w03-pnpm'` → `+ spike-kit-pkg 0.0.1`; lockfile `version: https://codeload.github.com/<owner>/<repo>/tar.gz/49091b40…` (the tagged commit) | None needed |
| S9b | Does `pnpm update <pkg>` move it when the tag moves? | yes | Tag moved to `d2c5660`: `pnpm install` kept `PKG-v1`; `pnpm update spike-kit-pkg` → lockfile `tar.gz/d2c5660a…`, `PKG-v2` | None needed |
| S9c | pnpm git dependency in CI with a PAT | not run | Needs a CI runner with a token | Test in the first CI pipeline that uses it |

## Side findings

| ID | Finding | Evidence |
| --- | --- | --- |
| 1 | Removing a marketplace in one project uninstalls its plugins in every project on the machine | `claude plugin marketplace remove spike-gh` in project 2, then `claude plugin uninstall spk-gh@spike-gh` in project 1 → `Plugin "spk-gh@spike-gh" not found in installed plugins` |
| 2 | A plugin skill with `paths:` is listed in every session, even before a matching file is touched; its body loads only when the model invokes it | Plain `claude -p x` transcript lists `spk-core:spk-svelte` in `skill_listing` |
| 3 | The desktop app starts Claude Code with `DISABLE_AUTOUPDATER=1`, which turns the plugin auto-update pass off | Debug log: `Plugin autoupdate: skipped (auto-updater disabled)` |
| 4 | A plugin skill that reads the plugin's own files (`references/`, `assets/`) with the Read tool is reading outside the project: each read asks for permission, and a headless run denies it. Seen with `--plugin-dir`; an installed copy in the plugin cache is unverified but sits outside the project too. Fix: a `bin/` helper prints the bundled document (the `sdlc` plugin's `sdlc-kit show <doc>`) | Wave 1 `sdlc` lane, headless `claude -p` with `--plugin-dir` (PR #3) |
| 5 | `allowed-tools: Bash(<bin>:*)` in a plugin skill's frontmatter pre-allows that plugin's bare `bin/` command: it ran headless with no permission prompt. A `/session:git` command with `context: fork` still had its forked agent ask to approve `git status`, so a command's `allowed-tools` may not reach a forked agent | `sdlc` lane: `sdlc-kit` ran from `/sdlc-intent` and `/sdlc-plan` with no prompt (PR #3); `session` lane, headless run (PR #5) |
